# Harden and Evaluate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the v1 hardening work: a resumable, race-safe `DELETE /account`; sanitized logs, 14-day retention and alarms for every Lambda and queue; a synthetic classification evaluation that fails CI on a quality regression; and a written map from every PRD acceptance criterion to an automated test or a controlled live check.

**Architecture:** Account deletion is a small state machine on the Users record. The API Lambda only does the fast, safe part (validate the confirmation, set `deletion_state = deleting`, bump `generation`, clear `active_run_id`, enqueue one job) and returns 202. Because every sync write, AI reservation, and dispatcher start already conditions on `generation`, that single conditional write stops all background work. A dedicated deletion Lambda, driven by its own SQS queue, then revokes the Gmail grant (best effort), deletes the owner's partitions in bounded, idempotent batches, wipes the profile, deletes the Cognito user, and leaves a small expiring tombstone so a still-valid access token cannot write data back. The existing 15-minute recovery pass re-enqueues deletions whose lease expired. Evaluation is an offline runner under `backend/evaluation/` that feeds JSON fixtures through the real `process_message` pipeline on moto, with recorded provider stubs, and reports precision, coverage, and recall with uncertainty.

**Tech Stack:** Python 3.12, FastAPI, boto3, DynamoDB, SQS, Cognito, AWS SAM/CloudFormation, pytest/moto, React/TypeScript/Vitest, GitHub Actions.

**Spec:** `docs/IMPLEMENTATION_ROADMAP.md` Milestone 10; `docs/PRD.md` sections 3 (Settings), 7 (Privacy), 8 (Acceptance criteria 1-14 and quality targets); `docs/TECHNICAL_DESIGN.md` Storage, API boundaries (`DELETE /account`), Sync and recovery (generation, tombstones), Operations and verification.

## Global Constraints

- **Agents never run account deletion against the live development account or any real identity.** Offline tests use moto and stubs. Live deletion verification stays pending for the owner, or for a separate test identity the owner creates and approves in Cognito. No task, script, or checklist step is run by an agent against the owner's account.
- Owner comes only from verified authentication (API) or the job's owner (worker). `DELETE /account` takes a confirmation body and nothing else; no endpoint accepts an owner ID.
- Do not change the meaning of `generation`, `active_run_id`, or any existing guard. Deletion adds `deletion_state` conditions next to them; a record with no `deletion_state` behaves exactly as today, so no data migration is needed.
- Deletion is idempotent at every step and safe to run twice concurrently. Each phase is recorded on the Users record and advances only by conditional write.
- Logs carry run/request identifiers, counts, durations, and sanitized categories only (exception class names, provider name). Never log email text, subjects, senders, evidence, prompts, model output, keys, tokens, owner email, or exception messages.
- Synthetic data only, in tests, fixtures, and docs. The evaluation makes no network call and no live provider call; live provider and real-inbox evaluation stay out of CI and out of the repository.
- A path with no automatic updates is reported "unmeasured", never 100%.
- Public-launch privacy and Google verification are out of scope (owner follow-ups below). Build nothing for a later milestone.
- Commit after each completed, verified step with a conventional prefix.

## Review Focus

- **Deletion order and resumability:** the flag and generation bump happen before any external call or delete; the Gmail token is decrypted and revoked before the profile is wiped; Cognito is deleted only after every partition and the profile are empty; killing the job at any line and rerunning it finishes without error or duplicate side effects.
- **Races (each has a test):** a worker mid-page when deletion begins (commit fails, nothing written); a queued sync job delivered after (claim fails, acknowledged); a dispatcher scan or `start` racing the flag (no run is created, or the created run is swept); an AI reservation during deletion (rejected, counter not incremented); an AI settings PUT or Gmail callback during deletion (rejected, no Users resurrection); a retried or concurrent `DELETE /account` (one lease holder, no error); the same owner's token used after completion (410, no write).
- **Isolation:** deleting user A leaves user B's rows in all five tables, including an owner ID that shares a prefix with A's, and B's dispatch, sync start, AI budget, and API calls are unaffected.
- **Privacy of logs:** an exception whose message contains canary text (email body, key, token) never reaches any log record or stderr.
- **Evaluation honesty:** precision counts any wrong application or wrong changed field; recall counts relevant mail wrongly ignored; zero automatic updates prints "unmeasured"; thresholds cannot be met by deleting fixtures; synthetic results are labeled as not establishing real-inbox accuracy.
- **Least privilege:** only the deletion function can delete data-table items or call `AdminDeleteUser`; the email worker role gains nothing.

### Task 3: Deletion sweeper and Lambda handler

**Files:** Create `backend/app/services/account_deletion.py`, `backend/app/deletion_handler.py`, `backend/tests/test_account_deletion.py`, `backend/tests/test_deletion_handler.py`. Modify `backend/app/services/google_oauth.py` (add `revoke_refresh_token`), `backend/tests/test_google_oauth.py`, `backend/app/services/sync_dispatch.py` (add `recover_deletions`), `backend/app/dispatch_handler.py`, `backend/tests/test_sync_dispatch.py`.

**Interfaces:**

- `revoke_refresh_token(refresh_token, *, urlopen=urlopen) -> None` POSTs `token=` form data to `https://oauth2.googleapis.com/revoke` with a 5-second timeout, refuses redirects, treats HTTP 200 and 400 `invalid_token` as success, and raises `OAuthError` otherwise. The token appears only in the request body.
- `AccountDeleter.run(owner_id, lease_id, deadline) -> DeletionResult` (`done`, `continue`) drives the phases in order and records progress after each:
  1. `revoke_gmail`: read the Users record, decrypt `encrypted_token` with the existing cipher (`gmail_refresh_token` context), call `revoke_refresh_token`, ignore and log only the category on failure, and move on. Missing token is a no-op.
  2. `delete_partitions`: Applications, Events, and SyncRuns by `Query` on `owner_id` with a keys-only projection and `ConsistentRead`, deleted with `BatchWriteItem` in groups of 25, retrying `UnprocessedItems` with bounded backoff, paginating by `LastEvaluatedKey`; OAuthStates by a paginated `Scan` filtered on `owner_id`. The Events table includes every `gmail#` message tombstone, merge tombstones, and soft-deleted application items. After the sweep, a verification `Query` (`Limit=1`, consistent) per table must return nothing, otherwise loop again (bounded; then return `continue`).
  3. `wipe_profile`: replace the Users item with `{owner_id, deletion_state: deleting, deletion_phase: delete_login, cognito_username, lease fields}`, which removes the Gmail email and ciphertext, the AI ciphertext, hint, provider, counters, and history fields in one write.
  4. `delete_login`: `AdminDeleteUser` using the stored `cognito_username`; `UserNotFoundException` is success; the call is skipped when no username was recorded (local development).
  5. `finalize`: write the 24-hour tombstone.
- The handler consumes `{"kind": "delete_account", "owner_id": ...}` from SQS (BatchSize 1, partial batch response). It takes the lease, runs until about 60 seconds before the Lambda deadline, and then re-enqueues one continuation and returns `continue`; a failure returns the item as failed so SQS retries, and logs only `phase` and `category`. A duplicate or late delivery finds no live lease or a `deleted` state and is acknowledged.
- `recover_deletions(client, publisher, users_table, deletion_queue_url, now)` (called from the dispatcher `recover` mode) scans Users for `deletion_state = deleting` with no live lease and re-publishes the job, so an interrupted deletion finishes without any user action.

**Why SQS plus a dedicated function, not inline in the API Lambda:** the API Lambda times out at 15 seconds and a real mailbox holds well over a thousand Events rows plus any future growth, so an inline sweep needs either a bound the user must keep retrying or a recovery pass that runs deletes in the dispatcher. A queue job has a 300-second budget, continuations, a DLQ and alarm, and lets the first sweep start after the API timeout (`DelaySeconds=30`) so an in-flight API write has finished. It also keeps `DeleteItem`/`AdminDeleteUser` off the API role and off the email-processing worker. The cost is one more queue, function, and log group (Task 5).

- [ ] Write revoke tests with a stub `urlopen`: success, `invalid_token` treated as success, HTTP 5xx/timeout/redirect raise `OAuthError`, the token is only in the body, and no log or exception string contains the token.
- [ ] Write sweeper tests (moto, synthetic data): a full deletion of an owner with applications, merged/soft-deleted applications, 120 Events rows (paging forced with a small page size), SyncRuns, OAuth states, Gmail connection, and AI settings leaves zero rows for that owner in all five tables and a tombstone in Users; Gmail revoke is called once with the decrypted token and its failure does not stop deletion; `AdminDeleteUser` is called once with the stored username, `UserNotFoundException` is success, and it is never called before the partitions and profile are empty.
- [ ] Write resumability tests: interrupt (raise) after each phase and after each batch, rerun, and assert the end state is identical with no error and no second revoke after the profile is wiped; two concurrent `run` calls with one lease do work once; an expired lease is taken over; a `continue` result republishes exactly one continuation; the verification sweep catches a row inserted after the first pass.
- [ ] Write isolation tests: deleting `owner-a` leaves `owner-b` and `owner-ab` untouched in every table, and an OAuth state for B survives the scan.
- [ ] Write handler tests: duplicate, late, and wrong-kind messages are acknowledged without work; a failure returns a batch item failure and logs only phase and category; a finished deletion returns nothing to retry.
- [ ] Write recovery tests: a deleting user with an expired lease is re-published; a live lease, an `active` user, and a `deleted` tombstone are not; the daily dispatch still skips deleting users.
- [ ] Confirm the tests fail; implement; run focused and full backend tests, lint, and `git diff --check`; commit.

### Task 5: Infrastructure for deletion, alarms, retention, and optional notifications

**Files:** Modify `infra/template.yaml`, `scripts/deploy.sh`, `scripts/test_deploy.py`, `.env.deploy.example`, `backend/app/dispatch_handler.py` (queue URL env), `backend/tests/test_infra_timing.py` (or add `backend/tests/test_infra_operations.py`), `docs/DEVELOPMENT.md`.

**Interfaces and decisions:**

The email worker role is unchanged.

- Alarms (all `TreatMissingData: notBreaching`): `AccountDeletionDeadLetterAlarm` (same shape as the existing DLQ alarm); `Errors >= 1` over a period for `SyncWorkerFunction`, `SyncDispatcherFunction`, and `AccountDeletionFunction` (these catch crashes and import failures; ordinary sync failures do not raise because the worker returns `batchItemFailures`); a `AWS::Logs::MetricFilter` on the worker log group for `event=sync_worker_failure` into a custom metric with `SyncWorkerRepeatedFailureAlarm` (`Sum >= 3` over 15 minutes, which is "repeated", while one transient Gmail retry is not); and a `MetricFilter` plus alarm on `event=api_unhandled_error` in the API log group (`Sum >= 3` over 15 minutes). - Optional notification: parameter `AlarmNotifications` (`'true'|'false'`, default `'false'`); condition `SendAlarmEmail`; when true an `AlarmTopic` with an email `Subscription` whose endpoint is `!Ref BudgetEmail`, and every alarm lists `AlarmActions` and `OKActions` through `!If [SendAlarmEmail, [!Ref AlarmTopic], !Ref 'AWS::NoValue']`. ### Task 7: Synthetic classification evaluation in CI

**Files:** Create `backend/evaluation/__init__.py`, `backend/evaluation/run.py`, `backend/evaluation/metrics.py`, `backend/evaluation/thresholds.json`, `backend/evaluation/fixtures/rules.json`, `backend/evaluation/fixtures/ai.json`, `backend/tests/test_evaluation.py`. **Fixture format (JSON, synthetic only):** each scenario has `id`, `category`, `applications` (synthetic existing records with company, role, status, season, year, optional thread and requisition links), `message` (subject, sender, body text, thread ID, received-at), and `expected` (`outcome`: `applied | ignored | review_required`; for `applied`: `application` ref, `status`, `season`, `year`, with unmentioned cycle fields `null`). **Coverage (at least 70 rules scenarios and 20 AI scenarios):** clear applied/OA/interview/offer/rejection with a linked application; the same wording with an unlinked application, multiple roles at one company, and two cycles at one company; job ads, newsletters, "apply now" mail, and recruiter marketing; hypotheticals ("if you advance...", "we may invite you"); multi-role listings with and without a stage; forwarded mail; ambiguous identity (company only, partial role, different cycle); a September email naming Summer 2027 and one naming no cycle; chronological conflicts and manual-correction replay (older evidence, terminal reopen, later clear rejection after a manual Interviewing correction); unparseable messages; prompt-injection text in both paths (instructions to set a status, change another application, reveal a key); obedient recorded AI outputs with fabricated or out-of-text evidence; and recorded provider errors (invalid key, rate limit, outage) that must leave the rule outcome intact.

**Runner behavior:** build each scenario on moto with a fresh synthetic owner, run the real `process_message`, and read the application and stored outcome back. Rules-only run: no escalator. AI run: for each provider with recorded outputs, a `RecordedProvider` stub replays the output through the real `AiEscalator`, validation, and reconciliation with an enabled synthetic key; nothing else changes. The runner blocks sockets for the process, so any network attempt fails the run. It writes a Markdown and JSON report (also to `$GITHUB_STEP_SUMMARY` when set) with the fixture file SHA-256 and the commit.

**Metrics (`metrics.py`, unit tested separately):**

- **Automatic-update precision (rules-only, and per AI provider):** correct automatic updates divided by all automatic updates. An update is correct only if it is on the expected application and every changed field equals the label; a wrong application, a wrong or unsupported field, or an update where review/ignore was expected counts as an error. Report the count, errors, and a 95% Wilson interval. Zero automatic updates prints `unmeasured`.
- **Automatic-processing coverage:** the share of all scenarios whose final outcome is `applied` or `ignored` (handled without review), per path.
- **Detection recall (full pipeline):** among scenarios labeled relevant (`applied` or `review_required` expected), the share whose final outcome is `applied` correctly or `review_required`. Relevant mail wrongly `ignored`, or wrongly updated, is a miss. Also report automatic-update recall (correct updates over expected `applied`). The report states that Gmail candidate-search recall is not modeled and remains unmeasured until the authorized real-inbox sample exists.
- **Rules versus AI:** the AI table is labeled "recorded synthetic outputs; not real provider behavior".

**Thresholds (`thresholds.json`):** rules precision >= 0.98 with at least 25 automatic updates; each measured AI provider precision >= 0.98 (an unmeasured provider is reported, not passed or failed); detection recall >= 0.90; minimum scenario counts (so deleting fixtures cannot satisfy the gate); and zero network attempts. `uv run python -m evaluation.run --check` exits non-zero on any breach and names the failing scenarios. Also use the fixtures to review the Milestone 9 deferrals: whether the 70-character quote cap nulls legitimate status sentences, and whether the status cue lexicon misses the fixture wording. Report any change as a numbered finding; do not tune the lexicon without the owner's review.

## Open Decisions

- **Tombstone after account deletion.** The plan leaves a 24-hour `{owner_id, deletion_state, deleted_at, expires_at}` Users item (TTL) so a still-valid one-hour access token cannot write data back. It holds no email, name, or content, only the opaque Cognito subject. If the owner wants no residual item, the alternative is relying on the 1-hour token lifetime alone and accepting a window where a stale token could recreate rows. Confirm.
- **Cognito username.** `AdminDeleteUser` uses the `username` JWT claim captured at request time. Cognito may also accept the `sub` as the username for admin calls, which would remove the stored field, but that was not verified; the claim approach does not depend on it. Confirm only if the stored field is objectionable.
- **API cost of the active-account check.** One consistent `GetItem` per request on the Users table. A cheaper variant checks only mutating routes, but it leaves reads available to a deleted account's token for up to an hour. The plan chooses the uniform check.
- **Retention of deleted-application history.** Deleting an application keeps its Events (including the `deleted` event's before-values and any applied-email evidence excerpts, at most 500 characters each) until account deletion, because PRD criterion 11 requires audit history and the design only calls for a minimal message-ID tombstone. Scrubbing those rows on application delete is a separate, unplanned change; the UI has no application-delete control today, so there is nothing to disclose yet. If a control is added, it must carry the tombstone disclosure. Confirm retain-until-account-deletion.
- **OAuth states.** Pending OAuth states are removed by a filtered scan during deletion and otherwise expire by TTL within minutes to 48 hours; a state also becomes unusable at once through the generation bump. Adding an owner index is not planned.
- **Disconnect does not revoke.** Gmail disconnect still only deletes the stored token and does not revoke the grant at Google. Revocation is added only for account deletion. Say if disconnect should revoke too.
- **Alarm thresholds.** `>= 3` worker failures per 15 minutes and `>= 3` unhandled API errors per 15 minutes are starting values for a single-user development stack. No API Gateway 5xx or latency alarm is planned.
- **Owner IDs in logs.** The plan logs run IDs but never owner IDs or emails. If operators need owner correlation, a keyed hash would be the safe option; not planned.
- **Evaluation thresholds are unproven until the first run.** The 98% precision and 90% recall gates and the minimum counts may fail on honest fixtures; the report decides whether that is a classifier defect or a threshold to discuss, and the owner decides.
- **Fixture authorship.** The agent writes and labels all synthetic scenarios; the PRD makes owner review of a small set of tricky examples optional. Offer the ambiguous-identity and injection scenarios for review.
- **Deletion queue and function.** A separate queue and function (not the sync worker, not inline) is chosen for least privilege, a longer time budget, and a DLQ; say if a lighter inline design with a recovery-driven continuation is preferred.
- **Who drives.** Claude Code drives and Codex reviews read-only, as in Milestone 9; the user has not restated roles for this milestone.
